01 — The Work

An accessibility-first redesign for Jasmine's Beat

An adaptive dance organisation whose own site excluded the communities it serves. I built the token architecture, the component states and the annotations that make those states legible to a screen reader, a keyboard and a voice command.

03 — The Problem

An adaptive dance organisation with a site its own community can't use

Jasmine's Beat teaches adaptive dance, but parts of its own community can't use the site. We audited the live site as a team and found four types of barriers: missing alternative text, broken structure with no semantic navigation, links that all read "click here," and text that fails contrast.

Individually, these are compliance issues. Together, they can stop someone from signing up for a class.

Two personas, built from the team audit

Enzo and Dex are composite users, not people we interviewed. Each represents a barrier we found in the audit and a task the live site currently makes difficult to complete.

Persona 01: Enzo, a dancer with a motor impairment who navigates by voice

He uses Dragon NaturallySpeaking, a voice-control tool that lets him navigate a computer by speaking, rather than using a mouse or keyboard.

On the live site, the classes page is a wall of text with no headings, and links like "click here" or "email to register" are difficult to distinguish by voice. The task can fail before registration even begins.

Persona 02: Dex, a Deaf parent looking for a class for his son

He judges a class by watching the studio videos and checking whether the instructor signs before committing his son to it.

The videos have no captions, and the instructor pages don't provide ASL (American Sign Language) or accessibility information. He has no way to evaluate the class before choosing it.

The personas are not edge cases. They are the audience.

We worked from Antoinette Carroll's equity-centred framework, which shifts the work from designing for to designing with.

And from Teresa Torres' continuous discovery: the team audit surfaced barriers, the personas explained their human cost, the redesign answered them, and the evaluative protocol tested whether the answer held.

04 — What I Learned

One audit. Two personas. Eighteen tasks that either complete or don't.

The finding everything else came from

A state you can only see in colour is a state that isn't there.

Every barrier the team rated critical came down to the same thing: meaning carried by something a person couldn't perceive. A disabled button that is only greyer. An error that is only red. A link whose purpose lives in the sentence around it rather than in the link. Fix that one class of failure and most of the task-blocking issues go with it.

Where that came from

4

barrier classes carried out of the team audit: missing alt text, broken structure, non-descriptive links, low contrast

18

evaluative tasks written across both flows, each mapped to a WCAG criterion and a severity rating

8

of those rated critical — the ones with no workaround, where the task is simply abandoned

Five rules I built to

01

Never colour alone. Every state changes its label text as well as its fill.

02

A link says where it goes. Out of context, read on its own, with no sentence around it.

03

One token, one decision. A colour is chosen once at the primitive tier and inherited everywhere else.

04

Focus is visible on every surface. 2px purple inside, 2px black outside, so the ring survives any background.

05

Write what the screen reader says. If the announcement isn't specified, it isn't designed.

05 — Key design moments

01

Three tiers so a colour is decided once

Design system

The problem

The same contrast failure kept returning

Contrast fixes kept coming back. Fixing a hex on one screen didn't stop the same problem from appearing elsewhere because the colour had no defined role.

Considered, not taken

A palette of approved hexes

Consistent, but it doesn't say where a colour belongs.

Two tiers: primitive → component

Simpler, but each component still has to decide what a colour means.

What I chose

Primitive → semantic → component The primitive holds the value, the semantic token gives it meaning, and the component decides where it is used. So a contrast fix happens once, at the level that owns it.
02

Writing what the button says out loud

Primary button

The problem

Every button state sounded identical

Different button states sounded exactly the same on a screen reader. Disabled, error, and success states could all be announced as "Register for Classes, button."

What I chose

The announcement changes with the state. A disabled button announces "Registration Closed." An error state announces that registration failed. The visual state and the screen reader announcement now describe the same thing.
03

Putting access information where the decision is made

Dex's flow

The problem

Access information arrived too late

Dex couldn't tell whether a class was right for him until he had already committed. Captions were missing from videos, and instructor accessibility information wasn't available when choosing a class.

What I chose

Put accessibility into the class experience. Instructor cards show accessibility training and the directory can filter by it. Videos include captions that describe both the music and movement cues. The information appears where the decision happens, rather than on a separate accessibility page.
04

Annotating heading hierarchy on every screen

Screen structure

The problem

No outline to navigate by

A screen reader user navigates by headings, not by looking. On the existing site, sections and card titles didn't have a clear structure.

What I chose

Define the hierarchy as part of the design. Every page has one H1, no skipped levels, and named landmarks. Focus order is documented alongside it so the way through the page is clear too.

06 — The handoff

Every component shipped with the details needed to build it

The handoff included the ARIA behaviour, screen reader announcements, keyboard interactions, focus states, colour independence, and WCAG criteria for each component.

Focus order was also documented in the prototype, so developers didn't have to work out the intended behaviour themselves.

What I'd measure next

Whether a voice-control user can register for a class without ever touching a mouse or asking for help.

Then the things a compliance table can't see: how long the task takes compared with a sighted mouse user, how often someone backtracks, and whether anyone abandons registration at the same point twice.

08 — What I'd Do Differently

01

The personas were based on an audit, not interviews

Enzo and Dex are personas built from the accessibility audit, not people we interviewed.

WhyWe didn’t have enough time to recruit people who use assistive technology — tools that help people interact with a computer in different ways — and conduct the interviews properly.
What this meansThe redesign is grounded in the barriers we found, but we haven’t tested whether it actually feels easier for the people represented by these personas.
Next stepTest the key tasks with four to six real participants before the redesign ships.
02

The announcements were written, not tested

Every screen reader announcement was written from the accessibility requirements, but we didn’t test how they actually sounded when read aloud.

Why it mattersA technically correct announcement can still sound confusing or repetitive when someone hears it.
What I’d do nextBuild the annotated states and test them with two screen readers — NVDA, a free Windows screen reader, and VoiceOver, Apple’s built-in screen reader — before signing them off.
