Making complex API documentation easier to use

Apex's documentation was a wall of text in a single theme with no way to navigate it.

I restructured it into a developer portal that technical and non-technical stakeholders could both use, and added a community so questions stopped disappearing into email.

Overview

Role — UX Design Intern

I was the sole designer on the developer portal, from research through the approved direction.

Timeline

10 weeks, Summer 2024

Focus

Developer experience, documentation UX, platform design

Context

Documentation is more than a support asset

Apex is B2B fintech. Its customers build on its APIs, so the documentation is often where they decide whether they can work with the platform.

Before

One long body of text No clear navigation No interactive examples No way to ask questions Light mode only
→

After

Layered developer portal Left-hand navigation + search Interactive examples Tutorials and videos Developer community Light and dark mode

The problem

Developers struggled to find what they needed.

Non-technical stakeholders struggled to understand it.

The cost

Trust.

When people cannot find an answer or understand the product, they can lose confidence in moving forward.

Final artifacts

The developer portal

1

A front door, not a document

The old experience dropped users straight into API reference, without explaining the product first. The new homepage gives a plain-language introduction to Apex, then directs users to guides, APIs, SDKs, or the sandbox.

2

Four ways in

The homepage brings Guides, API Reference, SDKs, and the Sandbox into view, so users can choose the path that matches what they need.

3

Try it on the homepage

Users can send a live API request and see the response immediately, without opening another page or setting up a separate tool.

4

Video for non-technical users

Stakeholders needed a way to understand Apex without reading API documentation, so tutorials and videos became part of the main experience.

5

Make the reference scannable

Instead of one long list of APIs, the reference is grouped into 12 clear API domains, making it easier for developers to find the area they need.

6

Somewhere to ask

When the documentation isn't enough, users can ask the community, contact Apex, or find more context through the blog.

Key design moments

Three decisions

01

Structure the page for two audiences

The problem

Two audiences, different needs.

Developers came looking for implementation details. PMs, founders, and CEOs needed to understand the product before making a decision. Putting both into the same content made the page harder to use.

Considered

Two separate paths

Technical documentation for developers Business documentation for stakeholders But separating them meant maintaining two structures—and made it easier for people to end up in the wrong place.

What I chose

One page, with information in layers

Start simple. A plain-language explanation gives everyone the context first. Show how it works. A visual makes the concept easier to understand before getting technical. Go deeper when needed. Reference details and code sit underneath for developers who need them.
↓
02

A portal, not just a docs page

The problem

Developers needed more than documentation. They wanted somewhere to try APIs, find examples, and get unstuck. Non-technical stakeholders needed videos, tutorials, and a way to ask questions. But there was no shared place to do any of this.

Considered

Keep support separate

Questions could go through comments or a support channel. But useful answers would stay scattered.

What I chose

Turn documentation into a developer portal

A searchable community alongside the docs gave users one place to:
Learn — tutorials, videos, and articles Build — API docs, examples, and testing tools Ask — questions and community answers
A question answered once could help the next developer too.
↓
03

Both themes, not the right one

The problem

Light mode only

Developers described eye strain during long documentation sessions. The docs were light mode only. I initially took their feedback to mean that dark mode should be the answer.

What I got wrong

Dark mode only

In interviews, developers told me dark mode was easier to read. The reasoning made sense, especially since most of them already worked in dark IDEs. So I designed around it. Testing showed that I had turned a preference into a constraint. Some developers still preferred light mode, and the better choice depended on the person, the environment, and even the time of day.

What I chose

Give people the choice

Instead of deciding which theme was better, I added a toggle that lets users switch between light and dark mode without leaving the page. The lesson was less about light versus dark mode and more about when not to turn user feedback into a design rule.

Research

What the research showed

I ran usability tests with 8 participants, 4 developers and 4 business stakeholders across product management, startup founders, and CEOs.

I was watching how each group navigated, where they got confused or slowed down, what built or broke their trust, and how non-technical stakeholders judged whether the platform looked credible.

Testing was where the project changed. One of my main decisions did not survive it.

Developers do not read, they hunt.

They scanned instead of reading, looking for organized sections and clear structure. Poor organization did not just slow them down, it lowered their confidence in the product. Structure was read as a signal of quality.

Everyone wanted to get to the examples.

Across all four groups, people wanted to interact with the APIs, test them, and find supporting resources. Clear organization and accessible examples were what made them feel confident using the product.

Non-technical stakeholders needed a different register.

Simple language, visuals, and video, plus an obvious way to ask a follow-up question.

Two types of user, one set of pages.

Technical users optimize for speed and want to skip ahead. Non-technical users optimize for confidence and need to be brought along. Every structural decision in this project came from that conflict.

Reflections

Designing for a domain I did not know

When I was asked to design for Apex, I knew very little about APIs, fintech, or how the product worked. It was intimidating to be asked to design for a space I barely understood.

So I spent my first few days learning the product and the domain before designing — understanding what Apex offered, how developers integrated it, and how similar platforms explained their products.

Once I had that foundation, I could design with the user's needs in mind rather than designing around assumptions.

The work got better once I stopped trying to sound like I already knew the space.

What I got wrong

I designed dark mode only, and I was confident about it. Developers had told me directly that it was easier to read, and the reasoning was sound. Usability testing showed I had solved the wrong problem. They did not want a better default, they wanted control, because the right theme changes with the room and the hour and the person.

I had treated a preference as a finding.

Now, before designing around something someone tells me, I ask whether it is actually a constraint or simply a preference.
